# Chrysopoeia Harness Product Specification

## Product Outcome

Chrysopoeia is a specialized trading-agent harness whose purpose is to find and
make good trades across markets. An operator sets session capital, a target win
rate, a trading window, and hard limits; the harness chooses markets, researches
them, and runs bounded research-and-decide cycles at a cadence of minutes or
longer. It has no overall strategy and accepts no human trade thesis or opinion.
Paper trading is the current mode. The approved product direction includes
automatic live trading on Polymarket with a dedicated small-balance wallet.
Authenticated execution remains disabled until the prerequisites and activation
checks below pass. A bounded harness invocation creates a complete reviewed,
policy-accepted trade-plan event; independent consumers own any paper or live
effects and their ledgers.

The core harness owns runtime-neutral canonical domain values and contracts for
snapshots/evidence, proposals/reviews, risk and cost policy, paper quote/fill,
workflow state transitions, audit output, and evaluation. LLMs propose and
review; they do not own authorization, risk, execution, accounting, or lifecycle
decisions.

## Phase 1: Local Harness

### Users And Use Cases

The user is an operator who sets session parameters and hard limits without
supplying trade ideas, market picks, strategies, theses, or evidence opinions.
Developers can evaluate the same behavior safely. They can:

- Configure validated capital, target win rate, trading window, agent count,
  exposure, loss, and model-cost values. The bounded loop enforces session
  capital, target, window, cycle, cost, loss, and stop limits.
- Let the harness select supported public markets and run bounded paper cycles.
  The local `run` command owns cadence and market selection. When the configured
  research model supports it, each captured market gets one bounded research step
  (Google Search grounding or OpenRouter web search); only normalized,
  snapshot-bound citations, never free-text model output, become citable
  evidence. Otherwise research is unavailable and the cycle proceeds on
  canonical snapshot evidence.
- Observe a cited proposal or abstention, independent review when applicable,
  deterministic decision, simulated fill or rejection, and cost record.
- Run deterministic tests/evaluations without credentials or model calls.
- Explicitly opt into a separately gated paid model behavior evaluation.

### Non-goals

- Unbounded autonomous trade creation. Agent proposal cycles remain bounded by
  operator-set limits. Any future consumer/venue exit monitoring and protection
  guarantees must be specified before live activation.
- High-frequency or latency-sensitive trading; cadence is minutes or longer.
- Operator-supplied strategy, theses, trade ideas, market picks, or evidence
  opinions. Human input is limited to session parameters and hard limits.
- Live/authenticated execution before its activation gates pass.
- Distributed or multi-user records, unbounded agent self-modification or tool
  creation, RAG/memory, or platform scheduling of proposal cycles. Bounded
  agent-approved context profiles from the existing tool registry are a future
  capability described below.
- Multiple agent runtimes. Each additional venue is a separate milestone and
  requires its own adapter.
- A generic plugin or custom model-provider framework; BYOK provider selection
  uses the existing ADK model boundary instead.

### Harness Definition And Ownership

A model proposes text or structured actions. The harness selects bounded context
and tools, validates and authorizes requests, executes allowed actions, records
observations, enforces limits, and decides whether work continues or reaches a
terminal outcome. Model decision, permission, and execution are distinct.

Chrysopoeia uses this hierarchy:

- **Session:** one operator-configured harness session. Current in-process paper
  financial records are durable in the local journal; active ADK conversation
  state is in-memory. Future consumers own separate ledgers.
- **Turn:** one requested paper cycle or operator action from input to outcome.
- **Step:** one trader, reviewer, or other model request and response.
- **Tool/action:** a bounded operation such as snapshot capture or context query.
  Deterministic validation, policy, quote/fill, and finalization are harness
  actions, not model tools.

This is a **Level 2 specialized agent harness** containing bounded **Level 1
turns**. ADK owns the inner model loop for each current agent invocation, while
Chrysopoeia constrains that loop inside its trading workflow. It is not a
**Level 3 meta-harness**: deploying the same harness as a managed or shared
service remains Level 2, even with autonomous looping and durability. It becomes
a meta-harness only if a control plane wraps multiple independent harnesses and
displaces or coordinates their session ownership.

OpenCode and official Claude Code are external engineering harnesses used for
development and review. Neither is an internal trading model provider or inner
product step, and neither is imported or a product dependency. OpenCode's
project orchestration rules remain applicable; Claude Code may read project
guidance. Claude Pro credentials authenticate official Claude Code only, never
Chrysopoeia inference or OpenCode. Product integration of either harness would
create Level 3/meta-harness scope and requires explicit design and product scope.

| Responsibility | Current owner | Chrysopoeia contract |
| --- | --- | --- |
| Context assembly and visible model tools | ADK agents plus Chrysopoeia instructions/tool registration | Core defines bounded canonical evidence and role separation; future profiles are constrained to the registered tool allowlist |
| Inner model loop and model request/response | ADK | Model output remains an untrusted proposal or review |
| Public market tools and normalization | Chrysopoeia Python integrated as ADK tools | Core owns canonical snapshot/evidence values |
| Policy and authorization | Chrysopoeia deterministic core | Must run near the exact paper effect; prompts do not authorize |
| Paper execution | Chrysopoeia deterministic core | Local simulation only; never exposed to trader or reviewer |
| Trade-plan event | Harness deterministic core | Produces `trade_plan_ready` only after review approval and hard-policy acceptance; the event is not an order or fill |
| Paper/live effects | Planned independent consumers | Each deduplicates by event ID and owns submission/simulation, monitoring, reconciliation, outcomes, and ledger |
| Deployment and trigger adapters | Platform | Invoke the Harness CLI without importing harness code; optional topic/IAM configuration supplies the Harness event sink |
| Cycle working state | ADK in-memory session state | The local journal is authoritative for in-process paper records; producer outbox metadata records delivery only and is never a consumer financial ledger |
| Terminal outcome | Chrysopoeia deterministic workflow | Model prose cannot fill, reject, or finalize a cycle |
| Audit and evaluation | Chrysopoeia deterministic records/assertions with ADK eval integration | Core owns required evidence and invariants |

The current logical states/outcomes are **configuring**, **ready/snapshot
captured**, **proposing**, **abstained**, **reviewing**, **rejected**,
**risk-rejected**, **filled**, and **failed**. Abstention, rejection, risk
rejection, fill, and unrecoverable failure stop the current turn. They are
encoded at three deterministic layers:

- **Turn graph:** each paper cycle is a fixed ADK workflow
  (`prepare trader input -> trader -> route -> reviewer -> finalize`, or route to
  abstention or unchecked-trade rejection). Code chooses the route; a trade
  reaches the reviewer only when its citations resolve and it matches the last
  passed plan check. Each terminal node records exactly one outcome status
  (`abstained`, `plan_check_rejected`, `reviewer_rejected`, `policy_rejected`,
  or `plan_ready`); a cycle without one fails closed.
- **Turn lifecycle:** the local journal admits a turn once, finishes it once
  with one known outcome, and accepts fills only for admitted, unfinished turns.
  Replay treats any violation as corruption and fails closed; interrupted turns
  are recovered or abandoned before new work.
- **Tool-call bound:** every model call reserves cost against the per-cycle
  model-call ceiling and daily budget, so the inner trader tool loop cannot run
  unbounded; the session loop stops on its cycle, cost, loss, deadline, stop, or
  signal limits.

Per-step conversation state inside a turn remains in-memory ADK session state;
there is no durable per-step event log.

Reason-act-observe is deliberately bounded here. Trader and reviewer steps
reason and propose; the harness captures a snapshot, selects canonical context,
validates citations, and performs deterministic policy, cost, quote/fill, and
finalization actions. Their resulting records are observations and audit
evidence, not permission for unrestricted iterative execution.

Model output is only a proposal. Citation validation, risk, cost, and paper fill
are deterministic failure boundaries. Cancellation or failure does not generally
prove that an external effect was absent; current paper-only effects are local,
so there is no authenticated venue effect to reconcile. Any future authenticated
path must persist intent before execution, use idempotency where supported, and
reconcile uncertain outcomes before retrying.

The bounded loop and turn recovery are implemented. Remaining Level 2 gaps
include distributed/multi-user operation, a sandbox, and human-approval
controls. The reviewer is an LLM role, not human approval.

### Adapter And Configuration Model

“Adapter” must be qualified by capability.

- The agent-runtime adapter integrates agents, model calls, workflow mechanics,
  session context, and agent tooling. ADK is the current adapter; its `Agent`,
  `Workflow`, callbacks, ToolContext/session state, and Agents CLI/A2A/eval
  tooling remain at the runtime edge.
- Configure a model through the selected agent-runtime adapter. The current ADK
  adapter runs the checked-in Gemini configuration. The model provider is BYOK
  and applies to every role, including context/research; research is selected by
  the context model (Google Search grounding for a Google model, OpenRouter web
  search for an OpenRouter model) and is otherwise unavailable. Local harness
  operation is a first-class path; managed deployment remains optional. Providers with
  ambient authentication use it (Vertex AI with ADC, never copied keys). Providers
  without ambient authentication read their key only from a provider-standard
  environment variable (e.g. OPENROUTER_API_KEY) in the operator's shell; keys
  never enter files, configuration, prompts, session state, logs, or journals.
  Model providers are selected through the existing ADK model boundary, not a
  bespoke plugin framework; only a configuration with offline contract tests and
  bounded live evidence is a verified path, and provider-specific logic does not
  belong in trading tools.
- Venue market data and paper execution are separate adapters. Venue adapters
  normalize into canonical runtime-neutral values. Configuring public market
  data never grants authenticated execution authority.
- The first venue adapter reads public Polymarket market metadata and CLOB
  depth. The current deterministic paper-execution implementation is local and
  depth-aware; it is not a venue order API.
- No abstract runtime Protocol/interface is required in Phase 1. Add another
  runtime adapter only when a second concrete runtime is required. External
  plugin discovery remains deferred until a real separately packaged adapter
  requires it.

The checked-in `chrysopoeia.toml` validates exact current identifiers and
settings, rejects unknown or mixed configurations safely, and selects the
current ADK/paper/Polymarket path. Roles may use different models only when each
has explicit pricing; unpriced models fail closed. The user operating
`daily_cloud_cost_budget` remains the sole daily-budget authority.
The current model is Vertex `gemini-3.5-flash` at the `us` model endpoint, with
non-global prices of $1.65 input and $9.90 text output per million tokens. The
model endpoint is independent of the deployment compute region.
Configuration must not imply that arbitrary
runtimes, models, or venues work before their adapters/configuration and contract
tests exist.

### Core Capability Boundaries

These are capabilities, not prescriptions for speculative classes:

- **Operating configuration:** validates user-controlled session capital,
  target win rate, trading window, paper limits, and cost limits.
- **Market selection and research:** the loop selects venue markets. Citable
  external Google Search grounding is implemented. The trader can call bounded
  financial-history tools for explicitly named stock and crypto instruments;
  they compute historical measurements as untrusted evidence and do not select
  markets or authorize trades. Financial statements and fundamentals remain
  planned.
  Polymarket is the current and only venue adapter; research providers are not
  venues.
- **Market-data capture:** obtains public venue data and normalizes one bounded,
  immutable canonical snapshot.
- **Evidence:** canonical snapshot evidence is always present. Local
  operator-supplied bundles are development/testing inputs. Bounded Google Search
  grounding and financial-history analysis are normalized into
  snapshot-bound URL/title/excerpt evidence; uncitable model prose is discarded.
- **Trader:** receives bounded snapshot/evidence context, may call bounded
  stock/crypto OHLCV analysis tools for a named relevant asset, and returns a
  structured trade proposal or abstention.
- **Reviewer:** independently receives the canonical snapshot, evidence, and
  validated proposal; it has no trader history or execution tool.
- **Market-specific context profiles (approved future capability):** deterministically
  route supported market families to versioned profiles containing bounded
  evidence sources and registered tool IDs. A stable market key scopes related
  trades and history to the instrument or event. For an unsupported market, a
  context-builder agent may draft a profile and a separate context-reviewer agent
  may approve it. The core enables it only after deterministic schema, registry,
  and resource-bound validation; no human approval is required for profiles
  limited to existing tools. Agents cannot create tools or change policy,
  execution authority, or global risk/accounting controls. Unknown or rejected
  profiles fail closed.
- **Deterministic policy:** checks identity, review, edge, exposure, executable
  depth, fees, and cost limits and fails closed.
- **Paper execution:** quotes/fills against local snapshot depth only after
  policy allows it; this simulation does not manage actual venue orders.
- **Trade-plan event:** after review approval and hard-policy acceptance, the
  harness produces a complete `trade_plan_ready` plan/request. Independent
  consumers may simulate paper effects or, after activation gates, execute within
  hard limits and reconcile venue state. Consumers have no agent/model authority.
  Two-sided paper trading was approved 2026-10-17: the trader chooses YES/Up or
  NO/Down, both bought from their actual token books. The forecast remains P(YES);
  `trade_plan_ready` v2 carries the chosen token's win probability and outcome.
  Existing YES-only v1 events remain valid. NO proposals/plan checks use
  `turn_outcome` v2 without changing the meaning of the forecast probability.
  This does not activate authenticated trading or authorize platform execution.
- **Audit and evaluation:** records terminal reasons, simulated fill data, and
  model-cost reservations/settlement, and verifies role/tool boundaries. Local
  forecast evaluation scores each binary market's first pre-close P(YES) (trade
  or abstain; Up counts as YES) with Brier against the Gamma-resolved outcome and
  the CLOB YES price at the same time. CS2 and Dota 2 match-winner markets are
  the primary, scored-only benchmark; BTC 5m automation is retired. This is
  forecast evaluation, not authenticated execution.

These canonical values, policy rules, transitions, and requirements belong to
the core harness, not ADK. Deterministic paper-cycle contracts, evidence, and
finalization are in `chrysopoeia/paper_cycle.py`; trading, risk, and fills are in
`chrysopoeia/trading.py`; and `chrysopoeia/agent.py` contains ADK runtime
composition, wrappers, tools, and workflow construction. Isolation is not
complete: `chrysopoeia/cost.py` retains ADK-edge cost callbacks, and agent
wrappers bridge ADK Context to core functions.

### Workflow

```text
run session: validate limits -> discover/select -> capture -> paper cycle
paper cycle: canonical snapshot -> bounded grounded search (+ optional local test evidence)
             -> trader -> abstain/report OR reviewer
             -> deterministic risk/cost -> rejection OR trade_plan_ready (target)
current: accepted plan -> optional durable outbox/direct sink -> in-process paper quote/fill -> journal/report
future: Pub/Sub trade_plan_ready -> independent paper or execution consumer
```

The reviewer is skipped on abstention. Finite workflow routes, canonical IDs,
and deterministic code—not model prose—control transitions. Journal-backed
`cycle` and `run` can opt into direct delivery through the durable producer
outbox. Harness drains pending events before work and confirms delivery before
acknowledgement.

### Trust And Safety Boundaries

- Tool and configuration inputs are untrusted and bounded before network or
  model use. External content is evidence, never instruction.
- Trader and reviewer have separate histories and permissions. Neither can call
  risk or execution functions directly.
- Proposal, review, snapshot, evidence, and fill retain one canonical snapshot
  and market identity. External evidence citations resolve only from the strict
  evidence set; current operator-supplied development/testing bundles remain
  untrusted evidence, never instructions.
- Market-data access carries no execution credentials or execution grant.
- Deterministic policy and model-cost limits cannot be weakened by an agent.
- Live execution remains disabled until all activation gates pass. It uses a
  separate isolated venue capability; market-data code cannot access signing
  credentials or submit orders.
- Secrets and sensitive data never enter source, prompts, session state, traces,
  logs, or tool results.

### Approved Live-Trading Direction

This records the approved design direction; it does not enable live orders.

- First live venue: Polymarket binary prediction markets; YES positions only.
- A CLI invocation, or future HTTP/request adapter calling the same core,
  produces `trade_plan_ready` only after review approval and deterministic hard-
  policy acceptance. Every decided turn also produces a journaled
  `turn_outcome`; failed or abandoned turns do not.
- The minimal envelope includes version/type, stable `event_id` across
  redelivery, creation time, market/snapshot identity, outcome, stake, maximum
  entry price, immutable ROI/time exit plan, review approval and policy/evidence
  references, and expiry/market end. It is a verified plan/request, not an order,
  venue fill, open position, or completed execution.
- Delivery may repeat. Each paper or execution consumer deduplicates by
  `event_id`, fetches fresh executable quotes instead of using the proposal
  snapshot as a current price, and owns its ledger, effects, and outcomes. There
  is no shared position journal between producer and consumers.
- No always-on harness process is required. Pub/Sub is the selected optional
  producer transport. The independent paper-only consumer is an authenticated,
  scale-to-zero Cloud Run service; live order mechanisms remain deferred. Its
  authenticated minute sweep owns paper exit monitoring.
- Use a dedicated operator-owned EOA funded with no more than $10 in trading
  collateral. Do not reuse a personal wallet. Wallet balance limits exposure but
  is not itself an application authorization control.
- Use Polymarket's official Python SDK behind the isolated execution adapter.
  Before integration, verify the current official package, supported wallet and
  signing flow, order semantics, and pinned version. Do not implement signing
  primitives in Chrysopoeia.
- Trading is automatic after the operator explicitly enables live mode. There
  is no per-order approval; deterministic code—not the trader or reviewer—owns
  hard limits, order validation, and the kill switch.
- The agent proposes the complete entry and exit bracket at trade creation, and
  the reviewer approves the bracket before the event is ready. The bracket is
  immutable after approval. Paper simulation supports full closes only.
- Opening trade plans include an entry limit and explicit exit policy: profit
  target, risk exit, and time/resolution behavior. A software-managed risk exit
  can be delayed if its consumer is unavailable, the market gaps, or executable bids are absent;
  targets use net proceeds at executable bid depth after fees, not a mid-price,
  and remain triggers rather than promised fill prices. Position sizing remains
  the hard maximum-loss control. Native conditional/resting orders versus
  consumer-side supervision is decided only after official SDK and venue
  behavior is verified.
  Any accepted/pending or uncertain order must be reconciled before retry or
  further trading.
- The runner checks Polymarket's geoblock endpoint at startup and fails closed
  when blocked or unable to verify. It never uses a proxy or other mechanism to
  bypass venue restrictions. The operator remains responsible for compliance
  with applicable local law and venue terms.

Pub/Sub is the selected optional producer transport. The Harness append-only
journal stores accepted event payloads and acknowledgements; enqueue precedes
local paper fill/finalization. Harness publishes configured sinks directly at
least once and acknowledges only after publish confirmation. Duplicate
publication is allowed and consumers deduplicate by
`event_id`. This is not a transaction with in-memory model state or exactly-once
delivery. Independent paper consumption is implemented without order authority.
Authenticated order placement remains future work subject to the gates below:

1. Paper-mode entry plans, exits, journal accounting, and recovery are complete.
2. The `trade_plan_ready` producer is implemented. Before independent consumer
   activation, its delivery contract is selected and implemented.
3. Consumers deduplicate redelivery and reconcile their own ledgers/effects. An
   execution consumer and venue also meet specified delivery, availability,
   restart-recovery, and exit-protection guarantees before live activation.
4. Live mode requires two independent opt-ins (validated configuration and an
   environment acknowledgement); neither model output nor stored session state
   can enable it.
5. Preflight verifies geoblock eligibility, account/order state, configured
   exposure and loss limits, and journal-to-venue reconciliation.
6. The isolated adapter enforces per-order, per-market, daily-loss, total
  exposure, price, and order-count caps at the effect boundary. Exact numeric
  limits are configuration decisions; live configuration fails closed if any
  required cap is absent and none may exceed the $10 funded trading balance.
7. A kill switch stops new orders, cancels all outstanding orders, records the
   result, and prevents restart until the operator resolves any uncertain state.
8. Order intent is persisted before submission. Retries use venue-supported
   idempotency or reconcile by order/trade identity; ambiguous outcomes halt
   rather than risk duplicate orders.
9. Fake-venue tests cover rejection, partial/pending fills, process interruption,
   reconciliation mismatch, geoblock, loss/exposure caps, and kill-switch paths.
10. The operator separately approves bounded live verification after all offline
   checks. Start with the smallest venue-accepted order, verify actual fill and
   exit reconciliation, and stop if cost, state, or bounds differ from plan.

Passing these gates does not authorize a live run by itself; each bounded live
verification still requires explicit operator approval under the verification
policy.

### Phase 1 Acceptance Criteria

Independent paper consumer acceptance:

- Strict bounded Pub/Sub envelopes and v1 events reject duplicate keys,
  constants, unknown fields, invalid identities/times, unapproved/unsupported,
  and expired plans before market requests. The consumer validates the
  Harness-owned shared JSON Schema as data without importing Harness.
- Valid plans use fresh bounded public metadata and YES books, then independently
  enforce identity/end-time, five-minute freshness, edge, entry, stake, exposure,
  depth, and configured paper-fee limits.
- Durable terminal fills/rejections precede HTTP success and deduplicate by
  `event_id`; terminal input/risk failures acknowledge, while quote/storage
  failures return 5xx for retry. Corrupt journals fail closed.
- The separate append-only consumer ledger replays after restart. A single Cloud
  Run instance, concurrency one, and serialized handlers enforce one writer.
- Authenticated minute sweeps full-close only on net-fee take-profit, stop-loss,
  or `exit_by`; insufficient bid depth retries later. Closed-market settlement
  requires unambiguous public YES/NO data and is idempotent.
- The consumer contains no models, credentials, signing, orders, or live effects.

Current harness acceptance:

- An explicit local cycle over seeded or captured Polymarket data terminates as
  abstained, rejected, or filled with an auditable reason.
- Trade proposals reach an independent reviewer; abstentions do not.
- Deterministic policy enforces canonical identity/citations, 5-point minimum
  edge, 1% per-market and 10% total exposure defaults, executable YES depth,
  explicit paper fees, and bounded model cost.
- Paper fills use depth-aware VWAP, include fees, and reject insufficient depth
  without partial fills.
- Every opening trade includes a reviewer-approved maximum entry price and
  immutable exit bracket: profit target, stop loss or explicit hold-to-resolution
  choice, and time/resolution behavior. The running paper loop enforces it from
  fresh, fee-adjusted executable bids; closes are full-fill only, and insufficient
  bid depth leaves the position open.
- Trader/reviewer model agents expose no execution capability in the canonical
  workflow evaluation.
- `cycle` handles one market; `run` owns bounded multi-cycle operation and
  journals the session, turns, fills, marks, full closes, and settlements locally.
- Journal-backed `cycle` and `run` preserve local simulation. When
  `CHRYSOPOEIA_EVENT_SINK` is a loopback HTTP URL or
  `pubsub:projects/<project>/topics/<topic>`, all outbox events are durably enqueued
  in journal order and acknowledged only after confirmed delivery. Pub/Sub
  messages carry string `record_type` and `schema_version` attributes. A set
  sink requires a journal and is validated before model work. Unset preserves
  local behavior with no Pub/Sub import or network access.
- Every decided turn is validated and journaled as `turn_outcome` before turn
  finalization. The single event sink publishes those outcomes and accepted
  `trade_plan_ready` plans to one topic for subscriber-side filtering; failed and
  abandoned turns are excluded. Context-attributed production decisions use
  `turn_outcome` v4, which adds the deterministic maximum reserved model-cost
  ceiling, including the configured research allowance. Recorded actual cost
  keeps its existing meaning. Readers continue to accept v3 history, and legacy
  context-free v1/v2 outcomes never gain an inferred reservation.
- Turn admission is idempotent and unfinished turns recover before new model
  calls. The loop stops at configured cycle, cost, loss, deadline, stop-file, or
  signal limits and reports completed-trade win rate against the target.
- The canonical offline suite and agent import pass without credentials or live
  model/network calls.
- Local evidence validation makes no network or model calls. A cycle adds at most
  one context call before trader/reviewer work; research failure is non-fatal, and
  trader and reviewer receive the same exact validated evidence list.

For every externally observable feature addition or change, acceptance also
requires both deterministic offline tests and a bounded live verification
against the real boundary changed. Covered boundaries include CLI behavior that
calls external services, venue adapters and data schemas, model/provider
configuration, callbacks and cost accounting, structured outputs, workflows,
A2A and serving endpoints, deployment/infrastructure, persistence, and any
future explicitly approved authenticated effect. Current examples are a
read-only public-data request for a venue change and a bounded paper cycle for a
model/runtime change; neither permits authenticated exchange execution.

Pure documentation, internal refactors with no externally observable behavior
change, and test-only tooling require offline verification of that claim but no
live run. Configuration-only changes that affect runtime or provider behavior
do require live verification. A live failure blocks acceptance and must be fixed
and rerun. Environment or IAM unavailability and vendor outages leave the
feature incomplete; they are not waivers and cannot be reported as verified.
Live verification is manual: first estimate cost and obtain approval for cost or
external effects, then exercise the smallest real path with bounded calls, time,
and data and least-privilege ambient authentication (ADC for Vertex) or, where
the provider lacks ambient authentication, a provider-standard
environment-variable key that never enters files, configuration, prompts, state,
logs, or journals. Sanitize and record the exact command, result, and cost when
applicable, and clean up or disable temporary resources. Offline pre-commit
checks remain mandatory; paid or network checks must not be added to pre-push or
other automatic hooks.

Adapter-configuration milestone acceptance:

- Model configuration is validated and applied through the selected
  agent-runtime adapter; the current implementation uses ADK's model boundary.
- Market-data and paper-execution adapter choices are independently validated.
- The existing Gemini and Polymarket defaults continue to work without claiming
  unimplemented runtime, model, or venue support.
- Each added adapter has offline contract tests against canonical inputs and
  failures plus bounded live evidence from its real boundary; market-data
  configuration cannot confer execution authority.

## Later Platform Evolution

Optional later capabilities include additional citable research providers, another agent-runtime
adapter, per-venue adapters beyond Polymarket, NO positions, agent
lifecycle/versioning, RAG/memory, and multi-tenant platform evolution. The
platform may launch the paper harness but does not schedule or drive its cycles.
Each capability requires its own acceptance criteria and explicit approval.

Cloud SQL remains the candidate authoritative relational store for a durable
platform. RAG and Memory Bank may supply provenance-linked context but can never
be authoritative for balances, fills, risk, or lifecycle decisions. See
`platform/docs/deployment.md` for the managed deployment profile.

### Market-specific context routing (approved future item)

Approved 2026-10-21 as a future Harness milestone, not current runtime
behavior. The trader may request a context for a market not served by an existing
profile. A context-builder agent drafts a versioned manifest using only
registered tools and approved evidence-source identifiers; an independent
context-reviewer agent approves or rejects it. A positive model review is
necessary but not sufficient: deterministic Harness validation enforces the
manifest schema, registered-tool allowlist, and resource bounds before enabling
the profile. This requires no human approval for a profile that uses existing
capabilities. Agents cannot add executable tools, weaken policy, or gain
execution authority. New tool families remain separate implementation work and
must pass their own offline contract tests and bounded live verification.

Route profiles from canonical market identity/type and scope context/history by a
stable market key (instrument/event and relevant interval/outcome). Prove that
tools and history do not cross market keys, malformed/rejected profiles fail
closed, and shared capital, risk, and accounting controls remain global.
Automated runs are limited to scored-only CS2/Dota 2 match-winner forecasting
(operator-approved 2026-11-07, replacing BTC 5m); enabling other automated market
families or automated paper trading requires separate scope and live
verification.

#### Outcome-driven profile iteration (approved future behavior)

Market contexts may evolve from the outcomes of trades made under that exact
context: deduplicated Harness/Consumer events -> deterministic, as-of,
context-scoped aggregates -> a curator-agent summary and proposed immutable
profile revision -> approval by a distinct context-reviewer agent -> use of that
version on later turns. Neither agent writes tools or executable code. The
profile validator limits instructions, evidence sources, and tools to the
registered allowlists and cannot change risk, accounting, policy, or execution
authority. No human approval is required for a local profile revision that
passes these gates.

Keep bundled, curated profiles in the Harness release and generated local
profiles in a persistent Harness-owned catalog separate from the financial
journal. Local profiles are not deployed automatically. Every turn pins its
profile ID/version/hash; the catalog retains the revision's source context,
outcome window, sample counts, and agent review result. Rejected or
under-sampled proposals do not replace the active profile. Initially, a revision
proposal requires at least 20 distinct closed/settled trade plans under the
active profile version for that context. Open positions, Consumer rejections, and
abstentions do not count as completed trade outcomes. Sparse outcomes are not
performance evidence, and historical profiles/outcomes are never rewritten.
Define forward-evaluation criteria before enabling automatic iteration.

### Trading-history context source (approved; implementation underway)

Approved 2026-10-12 as a future capability; coordinated implementation approved
2026-10-21. Harness `turn_outcome` v3 carries context scope/profile identity.
The independent Consumer publishes strict `consumer_outcome` v1 lifecycle
events (rejected, filled, closed, settled) to the existing topic; the Consumer
journal remains its ledger. Pub/Sub BigQuery subscriptions archive both event
types. A read-only Harness query joins Consumer outcomes to Harness decisions by
trade-plan event ID, filters by context scope/profile family and a bounded time
window, and enforces a maximum query size. It returns only bounded aggregates as
snapshot-bound, provenance-carrying untrusted evidence. It is never authoritative
for balances, fills, risk, or lifecycle; deterministic Python keeps every
decision. Sparse results are not performance claims, and older events are never
rewritten. Live IAM/query verification is still required before enabling the
optional history config.

### Independent insight observer (approved v1)

An independent observer work unit consumes Harness and Consumer event schemas as
data without importing their packages or sharing their journals. It has a
read-only identity and no execution, publishing, provisioning, or ledger
authority. V1 is pull-based: each read runs a deduplicated, partition-bounded,
byte-capped BigQuery archive query and returns bounded aggregates grouped by the
full context/profile identity. Report decisions, Consumer fills and final
outcomes, win rate, realized paper P&L, recorded actual model cost, and completed
trades against the 20-trade gate for that exact profile version. Never combine
profile versions to satisfy the gate. V3 and v4 decisions both contribute to
counts and actual cost. Report reserved cost only when every decision in a
profile/context group is v4 and supplies it; v3-only and mixed groups return
`null`, never a partial v4 sum beside all-version actual costs.

V1 retains no projection database or authoritative store and exposes no raw
event content. Only published archive events are visible, and analytics results
never drive balances, fills, risk, lifecycle, or execution. Subscriptions and
alerting are deferred to v2 until live alerts are needed. Deployment, IAM, and
event-schema changes require separate coordinated approval. Offline tests use
fake archive clients; a bounded live read is required before v1 completion.
